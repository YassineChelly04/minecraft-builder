🏗️ Minecraft Builder System Architecture

Multi-agent pipeline: Prompt → Intent → Shell + (Exterior ‖ Interior) → Repair → Critic → Commands

LLM Agent (uses Groq models)
Deterministic (Python logic)
Parallel Execution
Validation/Verification
Web/UI Layer

🔑 Key Design Principles

  • Deterministic Shell First: The foundation (floor, walls, roof, door, windows) is generated with Python logic, guaranteed to be watertight and valid. This is NOT left to the LLM.
  • LLM Agents Decorate Only: Exterior agent adds facade details (decorations). Interior agent adds furniture. Both are stripped of air blocks to prevent them from breaching the shell.
  • Parallel Execution: Exterior and interior agents run in parallel for speed (ThreadPoolExecutor with 2 workers).
  • Repair Layer Guarantees Validity: After merging outputs, the repair pipeline fixes block names, strips invalid block states, splits oversized /fill commands, and ensures every command is Minecraft-valid.
  • Model Configuration: Intent/Clarify/Critic use small fast models (8b). Build agents use strong spatial models (70b). Override via LLM_MODEL_* env vars.
  • Air Block Protection: The _strip_air() function ensures only the deterministic shell can place air blocks—this prevents LLM hallucinations from punching holes.
  • Optional Critic: User can enable/disable the critic via UI checkbox to stay within rate limits.

📊 Data Flow Summary

  • Input: User prompt + build origin (x, y, z)
  • Output: Dictionary containing: intent, exterior_commands, interior_commands, all_commands, valid (bool), errors, repairs (list), review (from critic), score
  • All returned commands are guaranteed to execute in Minecraft Java Edition 1.21.x
